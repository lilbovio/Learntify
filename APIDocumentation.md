# Learntify Study Plans API

This is the implemented REST CRUD API for the coursework presentation. It manages private study plans in a JavaScript learning platform. The professional focus is Software Engineering and Quality Assurance: clear contracts, testable responsibilities, persistent data, ownership checks and reproducible regression tests.

This guide covers study plans, not every Learntify endpoint. The machine-readable contract is [OpenAPI YAML](docs/college/openapi-study-plans.yaml). See [architecture, class, ER and sequence diagrams](docs/college/diagrams.md), [QA evidence and requirements](docs/college/QA_ENGINEERING.md), and [Bruno walkthrough](docs/college/bruno/README.md).

## Run and authenticate

Requirements: Node.js 24, pnpm 11.11.0, installed repository dependencies.

```sh
pnpm install --frozen-lockfile
pnpm db:local
```

In separate terminals keep `pnpm dev:accounts:server` and `pnpm dev:accounts:client` running. Use `http://localhost:5174` as the base URL; the client development server proxies API requests to local D1-backed Worker port 8788. These commands do not use the cloud database or send real email.

Authenticate through the [local mailbox flow](docs/LOCAL_ACCOUNTS.md) or the [Bruno collection](docs/college/bruno/README.md). The API uses an HTTP-only session cookie, not an API key or a manually invented JWT. Bruno has its own cookie jar; a browser login does not authenticate Bruno. Select the **Local** environment, rather than merely opening its editor. Variables are case-sensitive: `{{baseUrl}}`.

For POST, PUT and DELETE send `Origin: http://localhost:5174`. JSON bodies use `Content-Type: application/json`. Never put tokens, cookies, provider keys or private configuration in documentation or commits. Session ownership is derived by the server; clients cannot submit an owner ID.

## Resource and validation

A study plan contains `id`, `ownerId`, `slug`, `title`, `description`, `weeklyMinutes`, `status`, `createdAt` and `updatedAt`.

- `id`: server-generated UUID; immutable.
- `ownerId`: authenticated account; immutable.
- `slug`: 3–60 lowercase letters/digits, optionally separated by single hyphens. Immutable after creation; unique per owner.
- `title`: trimmed, nonblank, at most 120 characters.
- `description`: required string, at most 2,000 characters; empty is allowed.
- `weeklyMinutes`: integer from 15 through 1,200.
- `status`: `draft`, `active` or `completed`. POST always creates a draft; PUT supplies the status.
- Timestamps: generated by the server and returned as ISO date-time strings.

Unknown request properties are rejected. Two plans with the same description are allowed if their slugs differ. Status membership is validated, but no sequential lifecycle transition is enforced.

## Create: POST /api/v1/study-plans

```json
{
  "slug": "javascript-foundations",
  "title": "JavaScript foundations",
  "description": "Practice variables and arrays",
  "weeklyMinutes": 180
}
```

Success: **201 Created**, with `Location: /api/v1/study-plans/{generated-id}`. Illustrative response:

```json
{
  "data": {
    "id": "6f56c4bb-f15f-4c9d-bbc7-e32c64667f43",
    "ownerId": "example-owner",
    "slug": "javascript-foundations",
    "title": "JavaScript foundations",
    "description": "Practice variables and arrays",
    "weeklyMinutes": 180,
    "status": "draft",
    "createdAt": "2026-11-15T12:00:00.000Z",
    "updatedAt": "2026-11-15T12:00:00.000Z"
  },
  "meta": { "requestId": "example-request-id" }
}
```

Other rubric responses: **400** invalid body, **401** no session, **409** duplicate owner/slug, **500** unexpected internal failure. The database enforces duplicate protection atomically, including concurrent creation.

## List: GET /api/v1/study-plans?page=1&limit=20

Returns **200**, with `{ "data": [], "meta": { "requestId": "example", "page": 1, "limit": 20 } }` for an empty page. Nonempty `data` contains plan objects. Only the current owner's plans are returned.

`page` defaults to 1 and allows 1–10,000. `limit` defaults to 20 and allows 1–100. Optional `status` filters by one supported status. Unknown/repeated query parameters, zero, fractions and invalid values return **400**. Other rubric responses: **401**, **500**.

Order is `created_at DESC, id DESC`. Pagination uses offset/limit; concurrent inserts can shift later pages. There is no total-count field. An empty or out-of-range page is 200, not 404.

## Retrieve: GET /api/v1/study-plans/{id}

Returns **200** with the same data/meta envelope as creation. **400** means malformed UUID; **401** means no session; **404** means no record accessible to the current owner; **500** means an unexpected failure. Another user's plan is deliberately indistinguishable from a missing plan.

## Replace: PUT /api/v1/study-plans/{id}

```json
{
  "title": "Interview preparation",
  "description": "Explain functions and arrays out loud",
  "weeklyMinutes": 240,
  "status": "active"
}
```

Returns **200** with the updated data/meta envelope. Send all four editable fields, even when changing only one. Omitted fields or attempts to supply `slug`, `ownerId` or other immutable fields return **400**. This is not PATCH and does not create missing resources. Other rubric responses: **401**, **404**, **500**.

Updates preserve identity, slug and creation time; they update `updatedAt`. Concurrent updates use last-write-wins, without ETags or a revision precondition. Repeating the same PUT preserves editable values but can change `updatedAt`.

## Delete: DELETE /api/v1/study-plans/{id}

Returns **204 No Content** with an empty body. A subsequent GET or DELETE returns **404**. Only the selected owned plan is removed; lessons, attempts and notes are separate. Other rubric responses: **400** malformed UUID, **401** no session, **500** unexpected failure.

## Errors and operational responses

Example conflict response:

```json
{
  "error": {
    "code": "SLUG_CONFLICT",
    "message": "A plan with this slug already exists."
  },
  "meta": { "requestId": "example-request-id" }
}
```

Errors use an error/meta envelope. Clients should use status and `error.code`; messages explain the issue. Internal failures return `INTERNAL_ERROR` and a generic message, without SQL or stack traces. A request ID supports diagnosis.

Beyond the rubric, write requests can return **403** for an incorrect Origin, **413** for an oversized body, **429** for capacity limits, or **503** while writes are paused. Accounts can hold 50 plans. Application write reservations are limited to 2,000/account/day and 10,000 globally/day; these are not exact provider usage measurements.

Authentication and operational middleware can reject a request before field validation. For example, an unauthenticated malformed request returns 401 rather than necessarily 400. Test error cases with their other prerequisites satisfied.

The public alpha and the coursework demo have different readiness gates. The release record currently reports hosted private writes paused. Use the local account environment for the presentation; a passing local test does not prove cloud recovery or live authenticated persistence.
